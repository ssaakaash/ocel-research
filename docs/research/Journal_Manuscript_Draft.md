# How Much Does Flattening Hide? Predicate-Level Observability of Review Workflows in Case-Centric and Object-Centric Event Logs

## Abstract (draft)

Object-centric event logs (OCEL 2.0) keep the many-to-many structure of multi-entity processes, but most process-mining practice still flattens such data to one case notion. Prior work argues that flattening discards object-centric structure that matters for feature extraction and prediction; it does not say which concrete analysis questions become unanswerable. We propose **Cross-Object Observability Coverage (COOC)**, a predicate-level measure: the share of a registered set of process-rule predicates that a representation can express *and* answer identically to an object-centric oracle. We instantiate eight rule families (stage order, actor conflict, capacity, retry limit, finality, stall, deadline, o2o consistency) on eight public datasets: six simulated OCEL 2.0 logs, one real code-review corpus (CROP/Gerrit: 54,487 changes, 306,716 events after de-duplication) and one real education log (OULAD, 32,587 enrolments). Over 41 predicates, a single plain case-centric flat log answers 12.0 % (95 % CI 6.0–18.9) of them; building one flat log per object type raises this to 70.7 % (56.1–82.9). A denormalised flat export that keeps related object identifiers as columns reaches 28.4 % per log and 87.8 % with a portfolio of logs. Capacity rules need those identifiers; consistency rules that depend on object-to-object links and deadline rules that depend on object attributes remain unanswerable in every flat tier. Silent wrong answers were rare (0/29 plain, 1/72 denormalised). On the real review corpus, 53.1 % of the changes that have both an upload record and an approval show a person who did both (descriptive, not validated against human labels). These results characterise *what a flat export must carry* to answer a given agenda, not a universal quality score; they are bounded by our predicate selection and by the absence of independent human labels (reported as future work).

**Keywords:** object-centric process mining, OCEL 2.0, event data flattening, conformance, educational process mining, code review, process rules.

## 1. Introduction

Capstone, code-review, procurement and hiring workflows share a structure: a work item (project, change, order, candidate) passes through ordered stages, is touched by several actors, and consumes shared resources. Questions such as "did anyone approve their own submission?" or "was a reviewer overloaded?" involve at least two object types at once.

Process mining usually requires one case identifier per event. Van der Aalst (2019) describes the resulting deficiency, convergence and divergence; Adams, Park and van der Aalst (2023) argue that preserving object-centric graph structure improves machine-learning tasks in process mining (citation verified; full text not yet checked against our claim). What practitioners lack is a way to say *which of their questions* a given export can still answer. We contribute:

1. a **predicate-level observability measure (COOC)** with an explicit separation between *not expressible* and *expressible but wrong* (silent error);
2. **three representation tiers** that make the baseline fair: native OCEL (oracle), plain flat (pm4py semantics), denormalised flat (object identifiers kept as columns);
3. **eight public datasets** (two real) and an executable predicate registry, with an independent SQL cross-check of the oracle;
4. **findings on the capstone-style review lifecycle**, using Gerrit code review as the closest public analogue.

We do **not** claim to be the first to use OCEL in education (Miri et al., 2026) or to flatten-compare OCEL; our claim is the predicate-level, oracle-checked framing.

## 3. Method

### 3.1 Representations
Let *L* be an OCEL with events *E*, objects *O* (typed), event-to-object relations *R* ⊆ *E*×*O*, object-to-object links, and event/object attributes.
- **Native (oracle).** All of *L*.
- **Flat(T).** Case notion = object type *T*; one row per (event, *T*-object) pair; only event attributes survive. Convergence = events copied to several cases; deficiency = events with no *T*-object dropped.
- **Dflat(T).** Flat(T) plus, for each row, the identifiers of every other related object as columns; o2o links and object attributes still lost.
- **Leading(T, children).** Flat(T) that also pulls in events of declared child types reached via o2o; child identities lost.

### 3.2 Predicates and templates
A predicate is a template instance with a scope object type and declared requirements (object types, event attributes, activities, o2o links, object attributes). Templates: PREC (stage order), SODA/SODO (actor conflict via attribute or via object), LOAD (resource capacity, threshold = floor of the median peak concurrency on the native log), STALL, REPEAT (retry limit), AFTER (finality), DEADLINE (object-attribute deadline), CLOSURE (o2o consistency). The registry (`realdata/src/registry.py`) records every instance and rationale.

### 3.3 COOC and silent error
For representation *V* and predicate *p* with scope units *U*: *p* is **not expressible** if a requirement is missing from *V*; otherwise it is evaluated, and it is **correct** iff the set of flagged units equals the native oracle set, else a **silent error**.
COOC(*V*) = (# correct) / (# predicates evaluated). Native COOC is 100 % by construction (it defines the oracle); the oracle implementation is validated separately (§5.1). We also report **portfolio COOC** — a predicate counts if at least one flat log in the family answers it correctly (an upper bound that assumes the analyst knows which case notion to use).

### 3.4 Predicate positives
Predicates with ≥ 5 natural positives are evaluated on the original log (*natural*). Otherwise violations are injected by a minimal template-specific mutation (5 % of scope units, minimum 5) and the oracle is recomputed on the mutated native log (*injected*, no label file, hence no label leakage). Predicates still below 5 positives are excluded (4 of 45).

## 5. Results (preliminary)

### 5.1 Oracle validation
An independent stdlib-SQLite implementation reproduces the pandas oracle exactly on four CROP predicates (flagged changes: 522, 19,109, 164, 423; `realdata/results/sql_crosscheck_crop.json`). An independent CSV recomputation reproduces OULAD's 15,348 enrolments with ≥ 1 late submission, 415 submissions after unregistration, and the 29 flagged by the stage-order rule (25 submit before the registration day; 4 have no registration date). These checks test the predicate code, not the CROP converter. The converter was audited separately: a duplicate-event bug (17 % of event rows) and a missed "Patch Set N: Abandoned" form were found and fixed; a hand review of a stratified sample of classified comments found no further misclassification, but that review was done by the same author and is not an independent label set.

### 5.2 Coverage by representation (41 predicates, 8 datasets)

| Representation | COOC per single log | Portfolio of logs (one per type) |
|---|---|---|
| Native OCEL | 100 % (definitional) | – |
| Plain flat | **12.0 %** (CI 6.0–18.9; 46 views) | **70.7 %** (CI 56.1–82.9) |
| Denormalised flat | **28.4 %** (CI 18.5–38.3) | **87.8 %** (CI 78.0–97.6) |

CIs are percentile bootstrap (5,000 resamples) over views / predicates; predicates within a dataset are not independent, so the intervals are optimistic.

### 5.3 Coverage by rule family

| Family | Predicates | Plain flat portfolio | Denormalised portfolio |
|---|---:|---:|---:|
| Stage order | 17 | 100 % | 100 % |
| Retry limit | 3 | 100 % | 100 % |
| Finality | 2 | 100 % | 100 % |
| Stall | 5 | 80 % | 80 % |
| Actor conflict | 6 | 50 % | 100 % |
| Capacity | 4 | **0 %** | 100 % |
| o2o consistency | 2 | **0 %** | **0 %** |
| Object-attribute deadline | 2 | **0 %** | **0 %** |

Single-object rules survive flattening if the right case notion is chosen. Rules that need *identities of a second object type* survive only in the denormalised tier. Rules that need *o2o links* or *object attributes* survive in neither. The same actor-conflict rule on CROP is expressible in a plain flat log when the actor is an event attribute (CROP-2b) and not when it is only an object (CROP-2a): instrumentation, not representation alone, decides.

### 5.4 Silent errors
Plain flat: 0 of 29 answered predicate-view pairs wrong. Denormalised flat: 1 of 72 (1.4 %), a retry-limit rule on container logistics counted through a non-case object type; it appears in 8 of 10 injection seeds. **Hypothesis H2 (flattening mostly fails silently) is not supported by this evidence.**

### 5.5 Stability
Across 10 injection seeds on the six simulated datasets, the plain-flat shares are identical to three decimals and denormalised single-log share varies by SD 0.002. The measure is therefore determined by the structure of the predicate set, not by sampling noise, which is also its main limitation (§6).

### 5.6 Natural prevalence in the real data (descriptive; not validated against human labels)
- **CROP (54,487 changes, 306,716 events):** 19,109 changes have a person who both uploaded a patch set and approved: 53.1 % of the 35,963 changes that have both an upload record and an approval (35.1 % of all changes; 25 % of changes have no upload record because older Gerrit comments lack the "Uploaded patch set" line, so this is a lower bound on the rate among all changes); 522 (1.1 % of 46,285 merged changes) were merged without an earlier approval vote; 164 (0.3 % of 53,774 closed changes) have votes after merge/abandon; 423 (5.5 % of the 7,626 changes with any request-changes vote) exceed three request-changes rounds; 584 stayed open > 90 days after first upload; 269 participants exceed the median-peak load threshold.
- **OULAD (32,587 enrolments with at least one event; 32,593 in the registration table):** 25 enrolments submit before the registration day and 4 submit with no registration date (together the 29 flagged); 415 submit after unregistering; 15,348 (47.1 % of enrolments, 59.4 % of the 25,843 with submissions) have ≥ 1 submission after the assessment deadline (28.4 % of 173,912 submissions).
- **Flattening distortion (Angular, real):** a branch-case flat log has 81.6 × the event rows (99.99 % of events converge); a file-case log 6.5 × (63.5 % convergence, 59.6 % divergence).

## 6. Threats to validity (must be addressed before submission)
1. **Predicate selection bias.** I (the author of this draft) wrote the predicates after reading each dataset's vocabulary, so the denominator is not blind. The registry was fixed before flattening results were computed, but two degenerate rules (always violated) were removed and the LOAD threshold rule was changed from the 75th percentile to the median after a first run, both disclosed here and in `registry.py`.
2. **Structural determinism.** A flat log can only answer a predicate whose requirements it contains, so COOC largely mirrors the distribution of predicate scope types. The measure is a diagnostic for a stated agenda, not a discovery about data.
3. **Injection.** 21 of 41 predicates rely on injected violations; they test expressibility and exact agreement, not real prevalence.
4. **No human labels.** Whether "uploader = approver" is a true violation, or whether a late OULAD submission is a deviation, is not validated.
5. **Analogue transfer.** Gerrit, hiring and procurement workflows differ from capstone portals in rules and scale.
6. **Oracle circularity.** Native COOC = 100 % is definitional; only the SQL cross-check and the independent OULAD recomputation test the oracle code, and neither tests the data converters.
7a. **Converter and parser validity.** CROP vote labels are parsed with regular expressions from free text; "uploader = approver" uses the uploader of any patch set, not only the change owner, and 25 % of changes lack upload records. OULAD uses nominal term start dates, so cross-presentation timing is not meaningful.
7. **Simulated majority.** 6 of 8 datasets are simulated.
8. **Baselines.** A relational-source baseline (SQL on the original schema) is not separable from the oracle on public OCEL data and cannot be tested without a source schema we control; we do not claim OCEL outperforms direct SQL.
9. **No capstone data.** The paper contains no capstone-portal data; capstone relevance rests on the documented lifecycle and the Gerrit analogue.
