TEAM 1 — RESEARCH EXECUTION PROMPT FOR REVIEW 2

Role
Act as a research lead, process-mining engineer, data scientist, and academic reviewer for Team 1 only. The fixed project title is:
“Object-Centric Event Log Mining for Academic Capstone Processes: A Native OCEL 2.0 Approach.”

Primary objective
Prepare a defensible Review 2 research package showing how Educational Capstone Portal’s multi-object capstone lifecycle can be exported as OCEL 2.0, discovered, checked for conformance, analyzed for bottlenecks, and used in a lightweight digital-twin experiment. Because production Capstone logs and PDFs are unavailable, use a clearly labeled synthetic dataset derived from the documented Educational Capstone Portal state machines and domain model. Never present synthetic measurements as observed production results.

5. Current primary literature and official technical specifications for independently verified external claims.

Communication job
By the end, the Review 2 panel should understand that Team 1 has converted a documented platform workflow into a reproducible OCEL 2.0 research prototype, completed a substantial synthetic evaluation, identified measurable process risks, and has a credible path from synthetic validation to production-data validation.

4. Produce a pass/fail checklist covering literature and gap, objectives/methodology/architecture, 60–75% implementation and demo, draft report, outcome, and Q&A readiness.

Subtask 2 — Literature verification and novelty boundary
1. Verify the six Review 1 references using original papers/specifications/publisher pages.
2. Add only directly relevant primary sources on OCEL 2.0, object-centric process discovery/conformance, educational process mining, and organizational digital twins.
3. Build a comparison matrix with: source, setting/data, process representation, method, evaluation, limitation, and relevance to Educational Capstone Portal.
4. State novelty cautiously: the contribution is the application and instrumentation of a transactional, multi-object academic capstone lifecycle, not the invention of OCEL or process mining.
5. Flag any novelty claim that cannot be verified.

Subtask 3 — Educational capstone portal to OCEL 2.0 schema
1. Define event types from documented transitions: project creation, compilation started/succeeded/failed, student submitted, verification started, accepted, rejected, and scoring.
2. Define object types: Project, Student, Team, Faculty, Report, ReportVersion, Artifact, Score, and ReviewStage; add capacity or panel objects only when used by the experiment.
3. Create Event-to-Object and Object-to-Object mappings, including qualifiers.
4. Define dynamic attributes such as submission status, compilation status, review stage, remaining attempts, version, guide load, and score-lock state.
5. Produce a relational OCEL 2.0 mapping and a validation checklist for referential integrity, timestamps, actor attribution, and event ordering.

Subtask 4 — Synthetic dataset design and generation
1. Use a fixed random seed and record the generator configuration.
2. Default cohort: 120 projects, 360 students, 30 faculty guides, 1–4 report versions per project, and an R1/R2/R3 lifecycle.
3. Generate a clean baseline from the documented state machine.
4. Inject labeled anomalies tied to documented gaps/edge cases: R1 stage stall (G5), legacy/modular attempt-counter skew (G6/E15), unreachable REJECTED state (G7), attempts-exhausted deadlock (G9/E1), guide-capacity overrun (E5), enqueue orphan (E8), missing artifact path (E9), duplicate verification race (E10), NULL-score lockout (E12), and self-approval conflict (E14).
5. Make anomaly rates configurable; default to realistic low frequencies and include at least 25 positive anomaly cases for metric stability.
6. Export: event table, object table, E2O relations, O2O relations, anomaly ground truth, generator configuration, and dataset dictionary.
7. Label every table/chart generated from these files “Synthetic Educational Capstone Portal experiment.”

Subtask 5 — Baseline comparison: flattened log vs. OCEL
1. Produce project-centric, student-centric, and report-centric flattened logs from the same synthetic events.
2. Quantify event duplication, lost object relationships, ambiguous handoffs, and query-answer discrepancies caused by flattening.
3. Use representative multi-object events such as submission acceptance and score locking.
4. Report relation preservation and query accuracy alongside qualitative examples.

Subtask 6 — Discovery, conformance, and bottleneck analysis
1. Discover an object-centric directly-follows representation from the synthetic clean and anomalous logs.
2. Compare observed transitions with the documented state machines.
3. Compute transition conformance, audit coverage, actor attribution, deadlock rate, duplicate-verification rate, stage-progression rate, attempt-counter consistency, compile success rate, cache-hit ratio, p50/p95 compile time, review wait time, and total lead time.
4. Evaluate anomaly detection against injected labels using precision, recall, F1, and per-anomaly recall.
5. Report both aggregate values and confidence intervals or bootstrap variability where applicable.

Subtask 7 — Lightweight digital-twin experiment
1. Use an interpretable next-transition baseline first (frequency/Markov or calibrated tree model); treat a GNN as future work unless evidence justifies it.
2. Use chronological train/validation/test splits to avoid temporal leakage.
3. Report top-1 and top-3 next-transition accuracy, macro-F1, calibration error, and confusion matrix.
4. Simulate at least two interventions: relaxing remaining-attempt rules with an explicit recovery transition, and reallocating faculty capacity.
5. Compare intervention scenarios on deadlock rate, review wait time, stage completion, and policy trade-offs.
6. State that simulations estimate behavior under the synthetic model and do not prove real institutional impact.

Subtask 8 — Architecture and implementation evidence
1. Present the pipeline: documented Educational Capstone Portal AuditLog/domain model → schema mapper → synthetic generator/current extract → OCEL 2.0 validator/exporter → discovery/conformance → metrics → twin simulator.
2. Distinguish existing Educational Capstone Portal components from Team 1 prototype components and future production integration.
3. Create demonstrable artifacts: runnable generator, exported dataset, validation summary, analysis outputs, and a scripted demo path.
4. Provide a 60–75% implementation matrix using only artifacts that actually exist; do not infer completion from plans.
